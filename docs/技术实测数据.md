## 9. 滚轮模拟的三个致命坑（踩完才通）

实测日期 2026-11-27，验证方式：滚轮后对比截图像素差、再检查广告判定是否翻转。

### 坑 1：`CGEventCreateScrollWheelEvent` 在 pyobjc 下完全不工作

```python
# ❌ 无效：事件发出了，但 wheel 值没进去（Safari 上滚像素差 = 0.00）
ev = Quartz.CGEventCreateScrollWheelEvent(None, Quartz.kCGScrollEventUnitLine, 1, -15)

# ✅ 有效：用固定签名的 ...Event2（Safari 上像素差 = 44.97）
ev = Quartz.CGEventCreateScrollWheelEvent2(None, Quartz.kCGScrollEventUnitPixel, 1, -200, 0, 0)
```

原因：`...Event` 是 C 变参函数，pyobjc 绑定无法正确传递 wheel 值。**必须用 `...Event2`**。

### 坑 2：单位必须用 Pixel，Line 单位无效

`kCGScrollEventUnitLine` 即使配 `...Event2` 也无效，只有 `kCGScrollEventUnitPixel` 生效。

### 坑 3：iPhone 镜像必须先被点击，否则滚轮事件不转发给 iOS

- 激活 app（`activateWithOptions_`）返回 True，但 `frontmostApplication` 可能**仍是别的 app**
- 可靠做法：用 `CGEventCreateMouseEvent` 在窗口内**真实点击一次**（按下+抬起）
- 点击后 `frontmost` 确实变成 `iPhone镜像`，此时滚轮才生效
- 建议伴随分步 `kCGEventMouseMoved` 事件序列，让窗口感知「鼠标进入」

### 坑 4：方向

`SIGN = -1` 才是「上滑」到下一集。`+1` 也能让「上滑继续看短剧」文字消失，但方向不对（滑错），
**只看「文字消失」会误判成功** —— 必须再校验整窗画面是否恢复成有内容的视频。

### 最终可复现的最小代码

```python
import Quartz, time

def skip(px, py):
    orig = Quartz.CGEventGetLocation(Quartz.CGEventCreate(None))
    src = Quartz.CGEventSourceCreate(Quartz.kCGEventSourceStateHIDSystemState)
    # ① 移入
    Quartz.CGWarpMouseCursorPosition((px, py)); time.sleep(0.25)
    # ② 点击激活（关键）
    pt = Quartz.CGPointMake(px, py)
    for typ in (Quartz.kCGEventLeftMouseDown, Quartz.kCGEventLeftMouseUp):
        Quartz.CGEventPost(Quartz.kCGHIDEventTap,
                           Quartz.CGEventCreateMouseEvent(src, typ, pt, Quartz.kCGMouseButtonLeft))
        time.sleep(0.06)
    time.sleep(0.5)
    # ③ 像素滚轮，负值 = 上滑
    for _ in range(4):
        Quartz.CGEventPost(Quartz.kCGHIDEventTap,
            Quartz.CGEventCreateScrollWheelEvent2(
                None, Quartz.kCGScrollEventUnitPixel, 1, -300, 0, 0))
        time.sleep(0.03)
    time.sleep(0.35)
    Quartz.CGWarpMouseCursorPosition((orig.x, orig.y))   # 鼠标复位
```

## 11. 响应速度优化（2026-11-27）

### 用户反馈

原实现 3 秒一次检测，广告会显示 2 秒才被跳过，观感明显。

### 性能实测（决定能否提高频率）

用 `ps -o time` 取进程累计 CPU，跑 8 秒对比：

| 采样间隔 | 本进程 CPU | WindowServer CPU | 结论 |
|---|---|---|---|
| 1.0s | 0.38% | 42.4% | |
| 0.2s | 0.62% | 41.3% | |
| 0.05s | 1.12% | 37.6% | |

**关键发现**：每轮墙钟 18.6ms，但 **CPU 只耗 0.6ms** —— 那 18ms 是在等窗口服务器合成（阻塞等待，不占 CPU）。
WindowServer 那 40% 是视频解码+镜像的背景负载，**与采样频率无关**。

→ 结论：提高采样频率对系统几乎零成本，**可以直接按 0.5 秒甚至更频繁监控**。

### 采用的方案（组合）

1. **常态间隔 0.5s**（CPU 0.6%，可忽略）
2. **自适应快扫 0.15s**：亮度比上一次下降 >25% → 判定「可能进广告」→ 切快扫，持续最多 15 轮
   - 短剧画面本身的明暗变化会误触发，但代价只是短暂提速，无害
   - 实测日志：`亮度骤降 90→19 (79%) → 快扫模式`
3. **动作序列压缩** 1.74s → 0.69s
   - `move 5步×0.02` → `3步×0.01`
   - `sleep 0.25` → `0.12`
   - `sleep 0.5` → `0.25`（ACT_WAIT_FOCUS，太长没必要，太短会失效）
   - `sleep 0.35` → 去掉（由验证阶段的等待覆盖）
4. **跳过后退避** `1.2s` → `0.45s`，验证后 `2.5s` → `0.8s`

### 效果对比（实测日志）

```
# 旧（interval=3.0）
15:04:05,210  AD 命中 → 跳过
15:04:08,286  跳过成功          ← 3.1 秒

# 新（interval=0.5 + 快扫 + 压缩动作）
15:07:27,967  监控启动
15:07:28,030  AD 命中 → 跳过    ← 启动后 63ms 就命中
15:07:29,384  跳过成功          ← 1.35 秒
```

## 12. 多广告样式（关键坑）

优化上线后出现「广告一直在，不跳过」。诊断：

```
监控区 mean=24.3  text_px=358  ncc=0.413   ← 粗筛通过，但模板不匹配
```

存证图一看，是**另一种排版**：

| 样式 | 模板文件 | 排版 | NCC（对旧模板） |
|---|---|---|---|
| A | `template_ad_text.png` | `上滑继续看短剧 ⟨` 箭头在右 | 1.0 |
| B | `template_ad_text2.png` | `⟨ 上滑继续看短剧` 箭头在左 | **0.413** → 漏检 |

位置几乎相同（样式 A 的 x 0.3714~0.6214 / y 0.9291~0.9410；样式 B 的 x 0.3794~0.6221 / y 0.9300~0.9420），
**只是内容排版不同**，所以监控区覆盖没问题，纯粹是模板对不上。

### 修复

1. **多模板匹配**：加载 `assets/template_*.png` 全部，逐个算 NCC 取最高分
2. **未知样式自动存证**：粗筛通过（暗底+有文字）但所有模板都不达标 → 存 `UNKNOWN_AD_STYLE` 图 + WARNING 日志
   > `疑似新广告样式（模板未匹配 ncc=0.413, mean=24.3, text_px=358）存证=...UNKNOWN_AD_STYLE_001.png`
   > `→ 请把这张图加到 assets/template_ad_textN.png`
3. `reload_templates()` 支持热加载，加模板不用重启

### 以后再遇到漏检怎么办

```bash
# 1. 看有没有自动存证
ls -t logs/shots/ | grep UNKNOWN_AD_STYLE | head -1

# 2. 把它复制成新模板（命名要匹配 template_*.png）
cp logs/shots/<那张图> assets/template_ad_text3.png

# 3. 重启 app 即可，日志会显示「已加载 3 个模板」
./stop.sh && nohup ./run.sh >/tmp/app.log 2>&1 &
```

## 13. 模板匹配的根本缺陷 → 引入 OCR

### 又踩一次：第三种样式

```
监控区 mean=27.0  text_px=468  ncc=-0.04   ← 接近完全不相关
```

存证图一看：文字**向右偏移 + 字号更大**。模板和当前图叠在一起对比，位置差一截。

结论：**模板匹配对位置/字号极其敏感，广告样式可能是无限的**。
靠「遇到一种存一种」迟早还会漏，必须换成识别文字内容本身。

### OCR 方案（macOS Vision，免安装）

项目 venv 是 uv 建的，没有 pip，装不了 `pyobjc-framework-Vision`。
但可以直接**动态加载系统 framework**：

```python
import objc
ns = {}
objc.loadBundle("Vision", ns, bundle_path="/System/Library/Frameworks/Vision.framework")
req_cls, handler_cls = ns["VNRecognizeTextRequest"], ns["VNImageRequestHandler"]
```

### 实测数据

| 项 | 结果 |
|---|---|
| 识别速度 | **23ms**（fast 模式，`setRecognitionLevel_(0)`） |
| 首次调用 | 1030~1200ms（加载模型）→ **启动时必须预热** |
| 识别结果 | `['公上滑继续看短剧']` —— 左侧箭头 ⟨ 被认成「公」 |
| 误判测试 | 播放画面 15 次连续 OCR，**0 次误判**（只认出「，费观看」等无关片段） |

因为箭头会干扰，**不能要求精确匹配「上滑继续看短剧」**，改用关键词：

```python
AD_KEYWORDS_ANY = ("上滑", "继续看短剧", "滑继续看", "上滑继续")
```

### 踩坑：`options` 必须传 `None`

```python
# ❌ 报 ValueError: NSInvalidArgumentException - key does not exist
handler = VNImageRequestHandler.alloc().initWithCGImage_options_(cg, {})

# ✅
handler = VNImageRequestHandler.alloc().initWithCGImage_options_(cg, None)
```

### 最终判定链（三级）

```
① 粗筛（微秒级）
   mean < 60 且 text_px >= 300  →  否则 PLAYING
        ↓
② 模板匹配（0.1ms）
   任一 assets/template_*.png 的 NCC >= 0.70  →  AD（by=模板）
        ↓ 不达标
③ OCR（23ms）
   文字含广告关键词  →  AD（by=OCR）
   否则            →  PLAYING（by=OCR未命中）
```

- 模板路径最快，覆盖已知样式
- OCR 兜底，免疫排版/字号/位置变化
- 两者都不认时，`UNKNOWN_AD_STYLE` 存证 + WARNING，提示人工确认

### 当前已知 3 种样式

| 模板 | 排版 | 特点 |
|---|---|---|
| `template_ad_text.png` | `上滑继续看短剧 ⟨` | 黑底，箭头在右，NCC 对后两种 0.4 左右 |
| `template_ad_text2.png` | `⟨ 上滑继续看短剧` | 箭头在左，文字居中 |
| `template_ad_text3.png` | `⟨ 上滑继续看短剧` | 箭头在左，**文字右偏 + 字号更大** |

## 15. 监控区放大 + 模板滑动搜索（防位置漂移）

### 问题

第四种广告样式文字位置会漂，模板逐像素比对一偏就废（实测第 3 种 NCC = **-0.04**）。
用户提议：把监控区放大，防止文字左右上下不在固定位置。

### 关键结论：光放大区域没用，必须配「滑动搜索」

| 做法 | 效果 |
|---|---|
| 只放大区域 + 整区比对 | ❌ 更糟。模板必须缩放才能等比，位置偏移依然致命 |
| **放大区域 + 滑动搜索** | ✅ 位置怎么变都能找到（实测偏移 0~160px 全部 1.000 命中） |

用 `cv2.matchTemplate`（项目 venv 已有 cv2 + scipy），在大区域里滑动搜索模板：

```
放大区域 386x120 像素，模板 182x27
搜索位置数 ≈ 20000 个 → 耗时 0.65ms/模板
```

### 还发现一个隐蔽坑：模板 90% 是黑底

原模板是整块监控区截图，绝大部分是黑色背景。导致「黑底播放画面」也能拿到 **0.455** 的高分
（因为 NCC 对大片相同的黑底高度正相关），粗筛形同虚设，每轮都白跑 OCR。

**修复：加载模板时裁到文字包围盒**（留 4px 边距）：

| 模板 | 原始 | 裁剪后 |
|---|---|---|
| template_ad_text.png | 220×60 | **182×27** |
| template_ad_text2.png | 218×60 | **174×27** |
| template_ad_text3.png | 218×60 | **174×28** |

效果：
- 广告页 NCC：0.837 → **1.000**
- 播放画面 NCC：0.455 → **0.432**（那 0.432 来自底部的「选集·全81集·免费观看」，同样黑底灰字）

### 监控区参数变更

```python
# 旧：x 0.34~0.66  y 0.915~0.955   (111×30 逻辑点)
# 新：x 0.22~0.78  y 0.895~0.975   (191×60 逻辑点)
```

比实测文字范围（x 0.37~0.62 / y 0.929~0.941）左右各留了很大余量。

### 性能（关键：不要每轮都跑 OCR）

| 阶段 | 耗时 | 何时发生 |
|---|---|---|
| 粗筛 + 滑动搜索 3 个模板 | **2.0ms** | 每轮（0.5s） |
| OCR | 33ms（区域放大后，原 23ms） | 仅当模板分 ≥ **0.50** |

> 一开始放大区域后没调整粗筛，导致播放画面也通过粗筛、每轮跑 OCR，**detect 变成 82ms**。
> 改成「模板分 ≥ 0.50 才跑 OCR」后回到 **2.0ms**。

### 三级判定最终形态

```
① 粗筛 + 滑动搜索（2ms，每轮都跑）
   任一模板 NCC >= 0.70  →  AD（by=模板）
   0.50 ~ 0.70           →  跑 OCR 确认
   < 0.50                →  PLAYING（by=粗筛）
                              ↓ 但每 20 秒强制 OCR 一次兜底（by=OCR兜底）
② OCR（33ms）
   含广告关键词 → AD（by=OCR）
```

「每 20 秒兜底 OCR」是为了防止出现和已知样式**完全不相似**的新广告被永久漏掉。

---

## 16. 实测：OCR 救下第四种样式（带倒计时）

放大区域 + 滑动搜索上线后，第一次实跑就遇到：

```
15:29:23  AD 命中 {'mean': 9.46, 'text_px': 1655, 'ncc': 0.61,
                   'tpl': 'template_ad_text.png', 'by': 'OCR',
                   'ocr': '5s后可继续上滑观看短剧公'} → 跳过
15:29:24  跳过成功 → PLAYING 画面亮度=107.9
```

- 这是「**5s 后可继续上滑观看短剧**」—— 带倒计时的广告
- 模板 NCC 只有 **0.61**，达不到 0.70 的直判阈值
- 但 ≥ 0.50 触发了 OCR，识别出关键词「上滑」→ 判定 AD → 成功跳过

**这正好验证了三级判定的价值**：如果只有模板匹配，这种广告会漏检（0.61 < 0.70）；
如果只有 OCR，每轮 33ms、CPU 白烧。两者配合才对。

已知样式累计 4 种（模板目录只存了 3 个，第四种靠 OCR 兜着，可随时补模板）。
